� Component Deep Dive — Every Part Explained

🔌 Client Layer Components

📱
Application
Your Java, Python, Node.js, or any other application that needs to store/retrieve data. It communicates with PostgreSQL using a database driver (JDBC for Java, psycopg2 for Python, etc.). The application sends SQL queries and receives result sets.
🔌
libpq (PostgreSQL Client Library)
The official C library that handles the PostgreSQL wire protocol. All drivers (JDBC, psycopg2, node-postgres) ultimately use libpq or implement its protocol. It handles:
  • Connection establishment and authentication
  • Query transmission and result parsing
  • SSL/TLS encryption
  • Error handling and notification listening
🔁
Connection Pool (PgBouncer / HikariCP)
Since PostgreSQL forks a new process per connection (~2-5MB RAM each), connection pooling is critical.
  • PgBouncer: Lightweight external pooler (sits between app and PG)
  • HikariCP: Java-side pool (used with Spring Boot)
  • Pools reuse connections instead of creating/destroying them per request
  • Typical production setup: 100+ app threads share 20-50 actual PG connections

👑 Postmaster Process

👑
Postmaster (Main Supervisor Process)
The first process started when you run pg_ctl start. It's the parent of all other PostgreSQL processes.
  • Listens on port 5432 (or configured port) for incoming connections
  • Forks a backend process for each new client connection
  • Manages shared memory initialization at startup
  • Spawns background workers (WAL writer, autovacuum, etc.)
  • Handles crashes: If any backend crashes, postmaster terminates ALL backends and restarts (to ensure shared memory consistency)
  • Signal handling: Receives SIGHUP for config reload, SIGTERM for shutdown

Fun fact: Named "postmaster" because PostgreSQL was originally called Postgres (post-Ingres), and the supervisor was the "master" of the "post" system.

�🔷 Backend Processes

🔷
Backend Process (One Per Client Connection)
Each client connection gets its own dedicated Unix process (not a thread!). This is the "process-per-connection" model.
  • Complete isolation: One backend crashing doesn't directly affect others
  • Memory: Each backend uses ~2-5MB base + query-dependent work_mem
  • Handles entire query lifecycle: Parse → Plan → Execute → Return results
  • Accesses shared memory for buffer pool, locks, transaction status
  • Has private memory for query plans, sort operations, hash tables
  • Stateful: Maintains session variables, prepared statements, temp tables

⚠️ Why connection pooling matters: 1000 concurrent connections = 1000 processes = 2-5GB RAM just for backends!

🧠 Shared Memory Components

📦
Shared Buffers (Buffer Pool)
The most critical performance component — an in-memory cache of database pages (8KB each).
  • Purpose: Avoid reading from disk on every query
  • Size: Set via shared_buffers (recommended: 25% of RAM)
  • How it works: When a page is needed, check buffer pool first → if found ("buffer hit"), use it; if not ("buffer miss"), read from disk and cache it
  • Dirty pages: Modified pages are marked "dirty" and written to disk later by BGWriter/Checkpointer
  • Buffer replacement: Uses clock-sweep algorithm (similar to LRU) to evict cold pages

EXPLAIN (BUFFERS) shows: shared hit=1234 read=56 — hits are fast, reads are slow!

📝
WAL Buffers
In-memory buffer for Write-Ahead Log records before they're flushed to disk.
  • Purpose: Batch WAL writes for efficiency
  • Size: Set via wal_buffers (default: ~3% of shared_buffers, min 64KB)
  • Flow: Backend writes WAL record to buffer → WAL Writer flushes to pg_wal/ files
  • Commit behavior: On COMMIT, WAL must be flushed to disk (fsync) for durability
🔒
Lock Tables
Shared memory structures tracking all locks held by transactions.
  • Lock types: Row locks, table locks, advisory locks, relation extension locks
  • Lock modes: ACCESS SHARE, ROW SHARE, ROW EXCLUSIVE, SHARE, SHARE ROW EXCLUSIVE, EXCLUSIVE, ACCESS EXCLUSIVE
  • Deadlock detection: PostgreSQL runs deadlock detector every deadlock_timeout (default 1s)
  • View locks: SELECT * FROM pg_locks;
📊
CLOG (Commit Log / Transaction Status)
Tracks the commit status of every transaction using just 2 bits per transaction.
  • States: IN_PROGRESS, COMMITTED, ABORTED, SUB_COMMITTED
  • Purpose: MVCC visibility checks — "Is transaction 12345 committed?"
  • Location: pg_xact/ directory (was pg_clog/ in older versions)
  • Size: Very compact — 4 transactions per byte

⚙️ Background Processes

✍️
WAL Writer
Background process that flushes WAL buffers to disk files in pg_wal/.
  • Runs every: wal_writer_delay (default 200ms)
  • Also triggered: When WAL buffers fill up, or on COMMIT (if synchronous_commit=on)
  • Critical for: Durability — WAL must hit disk before transaction is considered committed
📤
Background Writer (BGWriter)
Writes "dirty" pages from shared buffers to data files on disk.
  • Purpose: Spread out I/O over time instead of big bursts at checkpoint
  • Runs continuously: Scans buffer pool, writes dirty pages with low urgency
  • Tuning: bgwriter_delay, bgwriter_lru_maxpages
  • Benefit: Reduces checkpoint I/O spikes, keeps some clean buffers available
✅
Checkpointer
Periodically creates "checkpoints" — consistent snapshots where all dirty data is written to disk.
  • Triggers: Every checkpoint_timeout (default 5min) OR when max_wal_size is reached
  • What it does: Flushes ALL dirty buffers, writes checkpoint record to WAL, updates pg_control
  • Why it matters: Recovery only needs to replay WAL from last checkpoint (not from beginning of time)
  • Spread: checkpoint_completion_target (default 0.9) spreads writes over 90% of checkpoint interval
🧹
Autovacuum
Automatically runs VACUUM and ANALYZE to maintain database health.
  • VACUUM: Removes dead tuples (from UPDATE/DELETE), frees space for reuse
  • ANALYZE: Updates table statistics for the query planner
  • Prevents: Table bloat, transaction ID wraparound (critical!)
  • Launcher + Workers: One launcher process spawns up to autovacuum_max_workers (default 3)
  • Thresholds: Triggers when dead tuples > autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × table size

⚠️ Never disable autovacuum in production! Transaction ID wraparound can cause data loss.

📊
Stats Collector
Gathers runtime statistics about database activity.
  • Collects: Table access counts, index usage, block reads/writes, sequential vs index scans
  • Stores in: pg_stat_* views (pg_stat_user_tables, pg_stat_activity, etc.)
  • Used by: Autovacuum (to decide what to vacuum), DBAs (for monitoring)
  • PG 15+: Rewritten to use shared memory instead of file-based collector (much faster)

💾 Storage Layer Components

💾
Data Files (Heap Files)
The actual files storing your table data on disk.
  • Location: $PGDATA/base/{database_oid}/{relfilenode}
  • Structure: 8KB pages containing tuple data
  • Max file size: 1GB (larger tables span multiple files: relfilenode, relfilenode.1, relfilenode.2, ...)
  • Page layout: Header → Item pointers → Free space → Tuples (grow from end)
📜
WAL Files (Write-Ahead Log)
Sequential log of all changes made to the database.
  • Location: $PGDATA/pg_wal/
  • File size: 16MB each (configurable)
  • Naming: 000000010000000000000001 (timeline + segment number)
  • Purpose: Crash recovery, replication, point-in-time recovery (PITR)
  • Guarantee: Changes logged to WAL BEFORE data file modification (hence "write-ahead")
📋
CLOG Files (pg_xact/)
On-disk persistence of transaction commit status.
  • Location: $PGDATA/pg_xact/
  • Size: ~256KB per 1 billion transactions (very compact)
  • Cleanup: Old segments removed after all transactions referencing them are gone
⚙️
Configuration Files
  • postgresql.conf: Main config — shared_buffers, work_mem, max_connections, etc.
  • pg_hba.conf: Host-Based Authentication — who can connect from where, using what auth method
  • pg_ident.conf: Username mapping for ident/peer authentication
  • Reload: Most settings reload with pg_ctl reload or SELECT pg_reload_conf();
  • Restart required: Some settings (like shared_buffers) need full restart

🔍 Query Pipeline Stages Explained

1️⃣
Parser
Converts raw SQL text into a parse tree (internal data structure).
  • Lexical analysis: Breaks SQL into tokens (keywords, identifiers, literals)
  • Syntax check: Validates SQL grammar (catches typos like SELEC instead of SELECT)
  • Output: Raw parse tree — knows structure but NOT whether tables/columns exist
  • Error example: syntax error at or near "..."
2️⃣
Analyzer (Semantic Analysis)
Transforms parse tree into a query tree with resolved references.
  • Name resolution: Looks up table names, column names in system catalogs
  • Type checking: Ensures operations are valid (can't add INTEGER + TEXT)
  • Implicit casts: Adds type coercions where needed
  • Error example: relation "users" does not exist, column "naame" does not exist
3️⃣
Rewriter (Rule System)
Applies transformation rules to the query tree.
  • View expansion: Replaces view references with their underlying queries
  • Rules: User-defined rewrite rules (CREATE RULE)
  • Updatable views: Transforms UPDATE on view to UPDATE on base table
  • Example: SELECT * FROM my_view → SELECT ... FROM base_table WHERE ...
4️⃣
Planner / Optimizer
The brain of PostgreSQL — generates the most efficient execution plan.
  • Cost estimation: Estimates I/O + CPU cost for each possible plan
  • Access paths: Sequential scan, index scan, bitmap scan, index-only scan
  • Join strategies: Nested loop, hash join, merge join
  • Statistics: Uses pg_statistic data (from ANALYZE) for row estimates
  • Parallelism: Decides whether to use parallel workers
  • Output: Execution plan tree (what EXPLAIN shows)

💡 This is why ANALYZE is critical — stale statistics lead to bad plans!

5️⃣
Executor
Actually runs the plan and produces results.
  • Volcano model: Each plan node is an iterator (open → next → close)
  • Pipelining: Results flow up the tree, one tuple at a time
  • Buffer access: Reads pages from shared buffers (or disk)
  • Parallel execution: Spawns parallel workers if plan says so
  • Output: Result tuples sent back to client

🔍 MVCC Deep Dive — How Concurrency Works

📝
What is MVCC?
Multi-Version Concurrency Control allows multiple transactions to see different versions of the same row simultaneously.
  • Readers don't block writers: A SELECT doesn't wait for an UPDATE to finish
  • Writers don't block readers: An UPDATE doesn't wait for a SELECT to finish
  • Only writers block writers: Two concurrent UPDATEs on the same row must wait
🏷️
Tuple Headers (xmin / xmax)
Every row (tuple) has hidden system columns that track its lifecycle:
  • xmin: Transaction ID that created this row version (INSERT or UPDATE)
  • xmax: Transaction ID that deleted/updated this row (0 if still valid)
  • ctid: Physical location (page#, offset) — the TID
  • Visibility check: "Is xmin committed AND (xmax=0 OR xmax not committed)?"

SELECT xmin, xmax, ctid, * FROM your_table; — shows hidden columns!

🔄
UPDATE Creates New Row Version
PostgreSQL UPDATE doesn't modify in-place — it creates a NEW tuple:
  1. Old tuple: xmax set to current transaction ID
  2. New tuple: created with xmin = current transaction ID
  3. Result: Both versions exist until VACUUM cleans up

⚠️ This is why UPDATE-heavy tables bloat and need regular VACUUM!

👁️
Snapshot Isolation
Each transaction sees a consistent "snapshot" of the database:
  • READ COMMITTED: New snapshot at start of each statement
  • REPEATABLE READ: Single snapshot for entire transaction
  • SERIALIZABLE: Like REPEATABLE READ + conflict detection
🧹
Dead Tuples & VACUUM
Old row versions ("dead tuples") must be cleaned up:
  • Dead tuple: A row version no longer visible to ANY active transaction
  • VACUUM: Marks space as reusable (doesn't return to OS)
  • VACUUM FULL: Rewrites entire table, returns space to OS (locks table!)
  • Autovacuum: Automatically runs VACUUM based on dead tuple thresholds

🔍 PG 18 New Components Explained

⚡
Async I/O (io_method = worker | io_uring)
The biggest architectural change in PG 18 — fundamentally changes how PostgreSQL reads/writes data.
  • Worker mode: Background processes handle I/O requests; backend continues CPU work
  • io_uring mode: Linux kernel feature for true zero-copy async I/O (fastest)
  • Benefits: Sequential scans 2-3x faster, VACUUM faster, index builds faster
  • Settings: io_method, io_workers, effective_io_concurrency
🔧
I/O Workers
New background process type dedicated to handling async I/O operations.
  • Count: Controlled by io_workers (default: 3)
  • Role: Receive I/O requests from backends, execute them, signal completion
  • Shared memory: Use ring buffers to communicate with backends
  • Benefit: Backends never block on disk; I/O workers absorb the wait time
📜
WAL Summarizer
New background process that summarizes WAL to track which data blocks changed.
  • Purpose: Enable incremental backups (only backup changed blocks)
  • Setting: summarize_wal = on (default in PG 18)
  • Output: WAL summaries stored in pg_wal/summaries/
  • Used by: pg_basebackup --incremental
  • Backup size reduction: 80-95% smaller than full backups
📊
Enhanced pg_stat_io
System view providing detailed I/O statistics by backend type and I/O context.
  • Dimensions: backend_type × object × context
  • Metrics: reads, read_bytes, read_time, writes, write_bytes, write_time, fsyncs
  • Use case: Identify I/O bottlenecks, tune buffer pool, validate async I/O benefit
  • Query: SELECT * FROM pg_stat_io WHERE reads > 0;
🧮
Virtual Generated Columns
Computed columns that don't store data — value is calculated at read time.
  • Syntax: column_name type GENERATED ALWAYS AS (expression) VIRTUAL
  • vs STORED: STORED columns occupy disk; VIRTUAL columns don't
  • Trade-off: Saves storage but costs CPU on every read
  • Best for: Simple expressions read infrequently, derived values
🔐
OAuth/OIDC Authentication
Native support for OpenID Connect authentication without third-party extensions.
  • Flow: Client gets token from IdP → sends to PostgreSQL → PG validates token
  • Providers: Works with Okta, Auth0, Keycloak, Azure AD, etc.
  • Configuration: New oauth auth method in pg_hba.conf
  • Benefit: Enterprise SSO, centralized user management, no password storage
🔢
Logical Replication of Sequences
Sequences can now be replicated via logical replication (previously impossible).
  • Problem before: After failover, sequences on replica didn't match primary
  • Risk: Duplicate primary key errors after failover
  • Solution: PG 18 includes sequence values in logical replication stream
  • Use case: High-availability setups, blue-green deployments
💾
Incremental Backups
pg_basebackup --incremental creates backups containing only changed blocks.
  • Requires: summarize_wal = on
  • Reference: Uses backup_manifest from previous backup
  • Restore: Use pg_combinebackup to merge full + incrementals
  • Benefit: Faster backups, less storage, less network bandwidth

🔑 Key Concepts Summary

📌
Remember these fundamentals:
  • Process-per-connection: Each client gets its own backend process
  • Shared buffers: The in-memory page cache (set to 25% of RAM)
  • WAL: Write-ahead logging ensures durability (write log first, then data)
  • MVCC: Multiple row versions allow concurrent access without read locks
  • Vacuum: Cleans up dead tuples left by MVCC
  • Cost-based planner: Chooses best execution path based on statistics
  • PG 18 Async I/O: Overlaps disk wait with CPU work — huge win for I/O-bound queries

🧬 What Gets Copied in fork()?

Understanding memory semantics when postmaster creates a backend process

✅ Copied (Copy-on-Write) Virtual Copy — Real Copy on Modify
🧠
Memory (Heap & Stack)
Process address space

What it is: The entire process memory — local variables (stack), dynamically allocated data (heap), global variables, and code.

How COW works: After fork(), both processes share the same physical memory pages. Pages are marked read-only. When either process writes, the kernel traps the write, copies ONLY that page, then allows the write.

PostgreSQL Impact:
• Backend inherits postmaster's ~15-50MB of initialized catalogs & caches
• Memory grows per-backend as queries execute (work_mem, hash tables)
• Each backend typically uses 2-10MB additional after fork()
📂
File Descriptors
Open files, sockets, pipes

What it is: Integer handles referencing open files, network sockets, pipes. Stored in kernel per-process file descriptor table.

After fork(): Child gets copies of all FDs pointing to same kernel file objects. Both share file offset position!

PostgreSQL Impact:
• Child inherits client_socket (FD for TCP connection)
• Child inherits listen_socket (then closes it)
• Parent closes client_socket (child owns it now)
• This is HOW the backend "takes over" the connection!
🌍
Environment Variables
PATH, PGDATA, LD_LIBRARY_PATH

What it is: Key-value pairs set in shell or process. Stored in process memory (typically at top of stack).

After fork(): Child gets exact copy. Modifications in child don't affect parent (and vice versa).

PostgreSQL Impact:
• PGDATA — data directory location
• TZ, LC_* — timezone/locale settings
• Backend inherits same config as postmaster
📡
Signal Handlers
SIGTERM, SIGHUP, SIGINT handlers

What it is: Functions registered to handle Unix signals. Signal disposition table stored per-process in kernel.

After fork(): Child inherits signal handler registrations. Child can then modify its own handlers.

PostgreSQL Impact:
• SIGTERM → graceful shutdown
• SIGHUP → reload config (reads postgresql.conf)
• SIGQUIT → immediate termination
• Backend resets some handlers after fork()
🔗 Shared (Same Physical Memory) All Processes See Same Data

How it works: PostgreSQL allocates shared memory using shmget()/shmat() or mmap(MAP_SHARED) at startup. This memory is mapped at the same virtual address in postmaster and all forked backends. Changes by any process are immediately visible to all others — this is how PostgreSQL coordinates!

📦
Shared Buffers
The buffer pool cache

What it is: In-memory cache of 8KB database pages. Set by shared_buffers (typically 25% of RAM).

Why Shared?
• Backend A reads page → cached in shared_buffers
• Backend B reads same page → instant hit (no disk I/O)!
• Backend A modifies page → B sees dirty version immediately
• Buffer pins + locks coordinate access
📝
WAL Buffers
Write-Ahead Log staging area

What it is: Buffer for WAL records before they're flushed to disk. Set by wal_buffers (default: 1/32 of shared_buffers).

Why Shared?
• Multiple backends INSERT concurrently
• Each appends WAL to shared buffer
• WAL Writer process flushes to disk
• LSN (Log Sequence Number) is globally coordinated
🔒
Lock Tables
Heavyweight & lightweight locks

What it is: Hash tables tracking who holds what locks. Includes relation locks, page locks, tuple locks.

Why Shared?
• Backend A: SELECT ... FOR UPDATE → acquires row lock
• Backend B: same row → sees lock, must wait
• Deadlock detector monitors global lock state
• pg_locks view reads this memory
📊
CLOG (pg_xact)
Commit Log — transaction status

What it is: 2 bits per transaction ID tracking status: IN_PROGRESS, COMMITTED, ABORTED, SUB_COMMITTED.

Why Shared?
• Backend reads row with xmin=12345
• Checks CLOG: "Is txn 12345 committed?"
• If yes → row is visible
• If no → row is invisible (MVCC magic!)
❌ Different (Unique Per Process) Kernel Assigns New Values
🆔
Process ID (PID)
Unique process identifier

What it is: Kernel-assigned unique integer (1-32768 typical, up to 4M on modern Linux). Returned by getpid().

PostgreSQL Impact:
• pg_stat_activity.pid shows backend PID
• pg_cancel_backend(pid) sends signal to PID
• Postmaster tracks child PIDs for crash handling
👨‍👦
Parent PID (PPID)
Who forked this process

What it is: PID of the parent process. Child's PPID = Parent's PID. Get via getppid().

PostgreSQL Impact:
• All backend PPIDs = postmaster's PID
• ps -ef | grep postgres shows hierarchy
• If postmaster dies, backends become orphans (PPID=1)
⏱️
CPU Time (Reset to 0)
User & system CPU counters

What it is: Cumulative CPU time consumed. Split into user time (your code) and system time (kernel calls). Tracked in struct rusage.

PostgreSQL Impact:
• Child starts with 0 CPU time (fresh slate)
• pg_stat_statements tracks per-query CPU
• Allows measuring backend resource consumption
🔐
File Locks (flock/fcntl)
Advisory & mandatory locks

What it is: Locks acquired via flock() or fcntl(F_SETLK). NOT inherited by child — must be re-acquired.

PostgreSQL Impact:
• Postmaster holds lock on postmaster.pid
• Prevents second postmaster on same data dir

💡 What's Happening?

  1. TCP Connection: Your app opens a TCP socket to PostgreSQL (default port 5432)
  2. Handshake: SSL negotiation (if enabled) + authentication (password, certificate, etc.)
  3. Postmaster fork(): The main postmaster process creates a dedicated backend for YOU
  4. Session begins: Your backend holds your connection state, prepared statements, temp tables

🔀 fork() Deep Dive

What fork() Does:
  • Creates exact copy of postmaster process
  • Copy-on-Write (COW) — memory shared until modified
  • Child inherits file descriptors (including client socket)
  • Both processes share access to shared memory
After fork():
  • Parent: Closes client socket, keeps listening
  • Child: Closes listen socket, keeps client socket
  • Child: Performs authentication
  • Child: Enters query processing loop
pid_t pid = fork();
if (pid == 0) {
    // Child process (new backend)
    close(listen_socket);
    BackendMain(client_socket);
} else {
    // Parent (postmaster)
    close(client_socket);
    // Continue accepting connections
}

💥
What if a Backend Crashes?

If ANY backend receives a fatal signal (SIGSEGV, etc.), the postmaster:

  1. Receives SIGCHLD notification
  2. Sends SIGQUIT to ALL other backends (immediate termination)
  3. Waits for children to exit
  4. Performs crash recovery (replay WAL)
  5. Respawns background workers
  6. Resumes accepting connections

Why terminate everyone? Shared memory might be corrupted — safer to restart clean.

🎯 Why This Matters

When you SELECT * FROM users WHERE id = 5:

  1. Executor asks: "Is page containing id=5 in shared buffers?"
  2. Buffer hit: Read directly from RAM → ⚡ microseconds
  3. Buffer miss: Read from disk → 💾 milliseconds (1000x slower!)

Goal: Maximize buffer cache hit ratio (aim for 99%+). Check with: SELECT * FROM pg_stat_database;

Write-Ahead Logging (WAL)

How PostgreSQL guarantees your data never gets lost

1️⃣ Transaction Starts

BEGIN; UPDATE accounts SET balance = balance - 100 WHERE id = 1;

2️⃣ Modify in Memory

Change is made in shared buffers (page becomes dirty)

3️⃣ Write WAL Record

WAL record written to WAL buffers: "Changed row X in page Y from A to B"

4️⃣ COMMIT

WAL flushed to disk (fsync). Now durable! ✅

5️⃣ Eventually...

Checkpointer writes dirty pages to data files (lazy, in background)

❌ Without WAL

Write directly to data files. If crash during write:

  • Partial page write = corrupted data
  • Lost transactions
  • Database inconsistency
VS

✅ With WAL

Write-ahead log first, then data. If crash:

  • Replay WAL from last checkpoint
  • All committed txns recovered
  • Database consistent
-- Check WAL settings
SHOW wal_level; -- replica (default) or logical
SHOW max_wal_size; -- 1GB default
SHOW checkpoint_timeout; -- 5min default

-- WAL usage stats
SELECT * FROM pg_stat_wal;

How PostgreSQL handles concurrent reads and writes

Each UPDATE creates a new row version. Old versions remain until VACUUM.

🔢 Transaction IDs

  • xmin: Transaction that created this version
  • xmax: Transaction that deleted/updated (0 if live)
  • Each transaction sees a "snapshot" of valid xids

🧹 VACUUM

  • Removes dead tuples (old versions)
  • Autovacuum runs automatically
  • Frees space for reuse
  • Never disable autovacuum!

🎭 Concurrent Transactions Example

-- Transaction A (xid=100) -- Transaction B (xid=101)
BEGIN; BEGIN;
SELECT * FROM users; -- Sees user.name = 'Alice'
UPDATE users SET name='Bob';
COMMIT; -- Still sees 'Alice'! (snapshot)
COMMIT; -- Now sees 'Bob'
