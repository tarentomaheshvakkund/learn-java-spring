🔐 JWT Authentication
Explained Simply

🏨 Think of it Like a Hotel Key Card
🎟️
Old Way: Session (Ticket Stub)
How it works:

1️⃣ Check in at hotel → Get stub: "A123"
2️⃣ Hotel keeps your info in logbook
3️⃣ Show stub at door → Guard checks logbook
4️⃣ Guard says "Yes, A123 = John Smith"

Problem: Guard must check logbook EVERY time! (Stateful)
💳
New Way: JWT (Smart Card)
How it works:

1️⃣ Check in at hotel → Get card with chip
2️⃣ Card contains: "John Smith, Room 301"
3️⃣ Card has special seal (can't fake)
4️⃣ Door reads card → Validates seal → Opens

Benefit: No logbook needed! Card has everything! (Stateless)
🎯 The Big Idea: JWT is like a sealed envelope with your identity inside. The seal proves it's authentic. No need to check a central database every time!

🆚 Stateful vs Stateless

🎟️ Session (Stateful)

How it works:
// 1. Login
Server: "OK, you're user 'john'"
Server stores: { "abc123" → "john" }
Sends cookie: "abc123"

// 2. Each Request
Client sends: "abc123"
Server looks up: "abc123" → "john"
// Must check database/memory!
❌ Cons:
  • Server must store sessions (memory/Redis)
  • Hard to scale (sticky sessions needed)
  • Database lookup on EVERY request
✅ Pros:
  • Easy to revoke (delete session)
  • Server has full control

💳 JWT (Stateless)

How it works:
// 1. Login
Server: "OK, you're user 'john'"
Creates token: { user: "john", exp: ... }
Signs with secret key
Sends: "eyJhbGc...xyz" (JWT)

// 2. Each Request
Client sends: "eyJhbGc...xyz"
Server verifies signature
// No database needed! ✅
✅ Pros:
  • No server storage needed
  • Easy to scale (any server can verify)
  • No database lookup
  • Works across microservices
❌ Cons:
  • Hard to revoke (valid until expiry)
  • Token can be large
Feature Session (Stateful) JWT (Stateless)
Storage ❌ Server Memory/Redis ✅ Client Side (Header)
Scalability ❌ Hard (Sticky Sessions) ✅ Easy (Any server works)
Database Hit ❌ Every request ✅ None (just verify)
Revocation ✅ Easy (Delete session) ❌ Hard (Valid till expiry)
Data Opaque ID (abc123) JSON Payload (username, role, etc)
Cross-Domain ❌ Cookie restrictions ✅ Works anywhere
Mobile Apps ❌ Cookies tricky ✅ Perfect fit

🔍 JWT Anatomy: What's Inside?

A JWT looks like: aaaaa.bbbbb.ccccc

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
.
eyJzdWIiOiJqb2huIiwiaWF0IjoxNTE2MjM5MDIyfQ
.
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
HEADER
Algorithm info
PAYLOAD
Your data (claims)
SIGNATURE
Security seal

1️⃣ HEADER (How it's signed)

{
  "alg": "HS256", // Algorithm: HMAC-SHA256
  "typ": "JWT" // Type: JSON Web Token
}

Just metadata. Says "I'm a JWT signed with HS256 algorithm"

2️⃣ PAYLOAD (The actual data - "Claims")

{
  "sub": "john_bond", // Subject (Username)
  "iat": 1516239022, // Issued At (timestamp)
  "exp": 1516249022, // Expires (timestamp)
  "role": "user" // Custom claim
}
⚠️ CRITICAL WARNING!

The payload is Base64 encoded, NOT encrypted!

Anyone can decode it and read it! Try it: jwt.io

NEVER put passwords, credit cards, or secrets here!
✅ OK: username, role, user ID
❌ BAD: password, SSN, credit card

3️⃣ SIGNATURE (The Security - Tamper Protection)

// How it's created:
HMACSHA256(
  base64(header) + "." + base64(payload),
  SECRET_KEY // Only server knows this!
)
🔒 This is what makes JWT secure!
✅ What happens:

1. Server creates token with secret key
2. Client receives token
3. Client sends token with each request
4. Server verifies signature with secret key
5. If signature matches → Token is valid ✅
❌ If hacker tries to tamper:

1. Hacker changes payload: {"role": "user"} → {"role": "admin"}
2. But hacker doesn't know SECRET_KEY
3. Signature won't match new payload
4. Server rejects: "Invalid signature" 🚫

🎭 Hacker Attack Demo: Why Signature Matters

Step 1: Original Token (Valid)
Header: { "alg": "HS256" }
Payload: { "user": "john", "role": "user" }
Signature: xyz123abc ← Created with SECRET_KEY

✅ Server validates: Signature matches!
Step 2: Hacker Tries to Change (Invalid)
Header: { "alg": "HS256" }
Payload: { "user": "john", "role": "ADMIN" } ← Changed!
Signature: xyz123abc ← Old signature (doesn't match new payload)

❌ Server rejects: "Invalid signature!"
❌ Access Denied: 403 Forbidden
Why Hacker Can't Win:
  • Payload is Base64 encoded (easy to decode and read)
  • Hacker can change payload easily
  • BUT! Hacker doesn't know SECRET_KEY
  • Without SECRET_KEY, can't create valid signature
  • Server checks: "Does signature match payload?" → NO → Rejected 🚫
🔑 The Secret Key is Everything!

Keep it safe! Never commit to Git! Never share it!
Use environment variables: JWT_SECRET=your-super-secret-key-here

What Your JWT Filter Does:

1
Check Authorization Header

Look for: Authorization: Bearer eyJhbGc...
If missing → Continue (user is anonymous)

2
Extract & Validate Token

Extract token from header
Verify signature with SECRET_KEY
Check expiration time
If invalid → Continue (user is anonymous)

3
Load User & Set Authentication

Extract username from token payload
Create Spring User object
Store in SecurityContextHolder
(This tells Spring "Hey, this user is logged in!")

4
Continue to Next Filter

Next filter checks: "Is user authenticated?"
If YES → Allow access ✅
If NO and URL requires auth → 403 Forbidden ❌

🔄 Complete Authentication Flow

Phase 1: Registration & Login
1️⃣ User Registers
POST /api/v7/auth/register
{ "username": "james", "password": "secret123" }

→ Server hashes password & stores in DB
2️⃣ User Logs In
POST /api/v7/auth/login
{ "username": "james", "password": "secret123" }

→ Server validates credentials
→ Creates JWT with username + expiration
→ Signs with SECRET_KEY

Response: { "token": "eyJhbGc..." }
Phase 2: Using the Token
3️⃣ Client Stores Token

Usually in: localStorage, sessionStorage, or memory
⚠️ Vulnerable to XSS in localStorage. Use httpOnly cookies for production!

4️⃣ Client Sends Token with Each Request
GET /api/v7/users
Authorization: Bearer eyJhbGc...

→ JWT Filter extracts token
→ Verifies signature
→ Sets authentication in SecurityContext
→ Controller receives authenticated user!
⚙️ Security Configuration
// SecurityConfig.java
@Configuration
public class SecurityConfig {

  @Bean
  public SecurityFilterChain filterChain(HttpSecurity http) {
    http
      .csrf(csrf -> csrf.disable())
      // CSRF protection OFF - we're stateless (no cookies)

      .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
      // Server forgets you immediately after each request

      .authorizeHttpRequests(auth -> auth
          .requestMatchers("/api/v7/auth/**").permitAll()
          // Open door: /auth/login, /auth/register

          .anyRequest().authenticated()
          // Locked door: Everything else needs JWT
      );

    return http.build();
  }
}
🎯 What This Does:

• CSRF Disabled: We don't use cookies, so CSRF attack doesn't apply
• Stateless: Server doesn't remember you between requests
• Public endpoints: /auth/login, /auth/register are open to everyone
• Protected endpoints: Everything else requires valid JWT

🏭 Production Considerations

1️⃣ Refresh Tokens

Problem: JWT valid until expiry. Can't revoke!

Solution: Short-lived access tokens (15 mins) + Long-lived refresh tokens (7 days)

• Access token expires quickly (limited damage)
• Refresh token stored in DB (can be revoked)
• Client uses refresh token to get new access token

2️⃣ HTTPS is MANDATORY!

Why: JWT sent in plain text header

Without HTTPS:
• Anyone on WiFi can sniff JWT
• Hacker steals JWT = Hacker becomes you!
• Man-in-the-middle attacks

⚠️ NEVER use JWT over HTTP in production!

3️⃣ Role-Based Access Control (RBAC)

Add roles to JWT payload:

{
  "sub": "james",
  "role": "ADMIN",
  "permissions": ["READ", "WRITE", "DELETE"]
}

Then in your controller:

@PreAuthorize("hasRole('ADMIN')")
@DeleteMapping("/users/{id}")
public void deleteUser(@PathVariable Long id) {
  // Only ADMIN can delete!
}
4️⃣ Token Storage (Frontend)

Options for storing JWT:

❌ localStorage: Vulnerable to XSS
⚠️ sessionStorage: Better but still XSS risk
✅ httpOnly Cookie: Best (not accessible to JS)
✅ Memory only: Most secure (lost on refresh)

📚 Summary

1️⃣
JWT = Smart Card with Seal

Contains your identity. Signed with secret key. Server verifies signature. No database lookup needed!

2️⃣
Three Parts: Header.Payload.Signature

Header = algorithm. Payload = your data (Base64, NOT encrypted!). Signature = security (HMAC with secret).

3️⃣
Stateless = Easy to Scale

No server storage needed. Any server can verify token. Perfect for microservices!

4️⃣
Signature Prevents Tampering

Hacker can change payload but can't fake signature without SECRET_KEY. Server rejects invalid signatures.

5️⃣
Production: Refresh Tokens + HTTPS + RBAC

Short-lived JWTs. HTTPS mandatory. Add roles for access control. Store safely (httpOnly cookies).
