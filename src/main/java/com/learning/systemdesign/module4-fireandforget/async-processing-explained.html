Customer orders food:

  • Chef cooks the meal (5 min) 👨‍🍳

Meanwhile (In Background):

  • Staff sends thank you card ✉️
  • Staff prepares gift basket 🎁
  • Marketing posts on social 📱
Benefit: Customer gets food fast! Other tasks happen later without blocking them.

🚨 What if ALL threads are busy AND queue is full?

Task is REJECTED! This throws an exception. You need to either:

  • Increase queue capacity
  • Increase max pool size
  • Or use a Message Queue (RabbitMQ/Kafka) for critical tasks
📊 How Thread Pool Processes Tasks
✅ Task 1-2: Core Threads Handle

Thread-1 and Thread-2 pick up tasks immediately

⏳ Task 3-502: Wait in Queue

Core threads are busy, so these tasks wait in the queue (capacity: 500)

🚀 Task 503-505: Emergency Threads

Queue is full! Create new threads (Thread-3, Thread-4, Thread-5) up to max pool size

❌ Task 506: REJECTED!

All 5 threads busy + Queue full (500 tasks waiting) = Task rejected with exception!

💻 How to Implement

Step 1: Configuration (Set Up Thread Pool)

// AsyncConfig.java
@Configuration
@EnableAsync // Turn on async support!
public class AsyncConfig {

  @Bean(name = "taskExecutor")
  public Executor taskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    
    executor.setCorePoolSize(2); // 2 threads always ready
    executor.setMaxPoolSize(5); // Max 5 threads if busy
    executor.setQueueCapacity(500); // Queue holds 500 tasks
    
    executor.setThreadNamePrefix("async-task-");
    executor.initialize();
    return executor;
  }
}

Step 2: Mark Method as Async

// WelcomeEmailListener.java
@Component
public class WelcomeEmailListener {

  @Async("taskExecutor") // THE MAGIC! 🪄
  @EventListener
  public void handleUserCreated(UserCreatedEvent event) {
    // This runs in 'async-task-1', NOT 'http-nio-8080-exec-1'
    emailService.send(event.email());
  }
}
⚠️ CRITICAL RULE: The method with @Async must be in a Spring Bean (separate class). Spring uses proxy pattern to intercept the call. If you call @Async method from same class, it won't work!

🤔 @Async vs Message Queue: Which to Use?
Feature @Async (In-Memory) Message Queue (RabbitMQ/Kafka)
Complexity ✅ Low - Just annotations! ❌ High - Need infrastructure
Setup Time ✅ 5 minutes ❌ Hours/Days
Reliability ❌ Low - Tasks lost if server crashes ✅ High - Persisted to disk
Scalability ⚠️ Vertical only (limited by one server) ✅ Horizontal - Add more consumers
Monitoring ❌ Basic logs only ✅ Built-in dashboards, metrics
Message Ordering ❌ No guarantees ✅ Can be guaranteed
Retry Logic ⚠️ Manual implementation ✅ Built-in retry mechanisms
Best For Welcome emails, logs, analytics, notifications Payment processing, order fulfillment, critical notifications
✅ Use @Async When:
  • Non-critical background tasks
  • Small to medium scale
  • Fast development needed
  • Task loss is acceptable
  • Single server application
🚨 Use Message Queue When:
  • Financial transactions
  • Order processing
  • Critical notifications
  • Need horizontal scaling
  • Microservices architecture

🌍 Real-World Analogy: Pizza Delivery

❌ Synchronous (Bad):

Customer calls pizza shop → Chef makes pizza → Chef personally delivers it to your house → Chef comes back → Only then answers next customer's call.

Result: Only 3-4 orders per hour! 😱

✅ Asynchronous (Good):

Customer calls → Chef takes order immediately → Hands to delivery driver (background worker) → Chef answers NEXT call while driver delivers.

Result: 50+ orders per hour! 🚀

📚 Summary: What Did We Learn?

1️⃣
The Problem

Synchronous code makes users wait for slow operations (emails, PDFs, notifications)

2️⃣
The Solution

Use @Async to run slow tasks in background threads. User gets instant response!

3️⃣
Thread Pools

Don't create new threads (expensive). Reuse a pool of worker threads efficiently!

4️⃣
When to Use What

@Async for simple cases. Message Queue (RabbitMQ/Kafka) for mission-critical production systems.
