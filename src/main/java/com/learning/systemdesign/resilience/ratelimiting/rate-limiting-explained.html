Module 13: API Rate Limiting

1. The Problem

Imagine your API is a popular restaurant. If one customer orders 1,000 dishes at once, the kitchen gets overwhelmed, and other customers can't get served.

In tech terms:

  • DDoS Attacks: Hackers flooding your server to crash it.
  • Resource Hogging: One script accidentally calling your API in a tight loop.
  • Cost Control: Preventing cloud bills from skyrocketing.

2. The Solution: Rate Limiting

💡 The Club Bouncer Analogy

Think of the Rate Limiter as a bouncer at a club.

  • Original Policy: "I only let in 5 people every minute."
  • First 5 people? "Come on in!" (200 OK)
  • 6th person? "Wait until the next minute starts." (429 Too Many Requests)

3. How We Implemented It

We used Resilience4j. It uses the "Token Bucket" algorithm.

Configuration (application.properties)

# The Rules:
resilience4j.ratelimiter.instances.basic.limit-for-period=5
resilience4j.ratelimiter.instances.basic.limit-refresh-period=60s

This means: "Give users 5 tokens. Refill the bucket with 5 fresh tokens every 60 seconds."

The Code

@GetMapping
@RateLimiter(name = "basic", fallbackMethod = "fallback")
public ResponseEntity<String> limitedEndpoint() {
    return ResponseEntity.ok("Success!");
}

4. What Happens When You Get Blocked?

If you exceed the limit, the server throws a RequestNotPermitted exception.

Usually, this translates to the HTTP Status Code:

429: Too Many Requests

In our implementation, we caught this exception in the fallbackMethod to send a friendly message.
