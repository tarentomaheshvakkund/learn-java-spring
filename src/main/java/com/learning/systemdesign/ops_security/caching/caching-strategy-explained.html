🔄 Cache-Aside Pattern (How It Works)
1 User Requests Data

GET /api/v6/users/123 → "Give me user 123"

⬇️
2 Check Cache First

Is User 123 in cache (RAM)?

✅ CACHE HIT

Found in cache!

→ Return immediately (1ms)
✨ Database not touched
🚀 Super fast response

❌ CACHE MISS

Not in cache!

→ Go to Step 3
🐢 Need to query database
⏱️ Slower response (50ms)

⬇️ (Only on Cache Miss)
3 Query Database

SELECT * FROM users WHERE id = 123
(This is the slow part - 50ms)

⬇️
4 Store in Cache for Next Time

cache.put("users:123", userData)
(Next request will be fast!)

⬇️
5 Return to User

User gets their data!
First time: 50ms (miss)
Second time: 1ms (hit)

🎯 "Cache-Aside" Name Explained:

The cache sits "aside" (next to) the main flow. App checks cache first, but if not there, it goes around to the database. It's "lazy loading" - only requested data gets cached.
☕ Spring Boot Makes It Easy: @Cacheable

Spring handles all the "check cache first" logic automatically!

// UserService.java
@Cacheable(value = "users", key = "#id")
public UserResponse getUserById(Long id) {
  // This line ONLY runs on Cache Miss!
  return userRepository.findById(id)...;
}

🔍 What Happens Behind the Scenes?

Step 1: Spring Intercepts Method Call

When you call getUserById(123), Spring's AOP proxy intercepts it

Step 2: Check Cache

Looks in cache named "users" for key "123"

If Found (Cache Hit):

Return cached value immediately
Method body NEVER executes
Database query SKIPPED ✅

If Not Found (Cache Miss):

Execute method body (query database)
Store result in cache
Return result

📝 Parameters Explained:

• value = "users" → Cache name (like a Map name)
• key = "#id" → The unique identifier (parameter value)
• Think: Map<String, Object> usersCache = {"123" → UserData}
😱 The "Stale Data" Problem

Caching introduces a trade-off: Speed vs. Consistency

🐛 The Bug Scenario:

1
10:00:00 - User Fetches Profile
GET /users/123 → Returns: { "name": "Alice" }
✅ Now "Alice" is cached in RAM
2
10:05:00 - User Updates Profile
PUT /users/123 → { "name": "Al" }
✅ Database updated to "Al"
😱
10:06:00 - Another User Fetches Profile
GET /users/123 → Returns: { "name": "Alice" } ❌
⚠️ STALE DATA! Cache still has "Alice" but DB has "Al"
📞 The Phone Book Analogy:

Imagine you have an old phone book (cache) with John's number as 555-1234.
John changes his number to 555-9999 (database updated).
But you keep calling 555-1234 because your phone book is outdated!

Solution: You need to update or throw away the old phone book entry!
✅ The Solution: Cache Eviction

When data changes, DELETE the old cache entry!

// UserService.java
@CacheEvict(value = "users", key = "#id")
public void updateUser(Long id, UpdateUserRequest req) {
  // 1. Update database
  userRepository.save(...);
  
  // 2. Spring AUTOMATICALLY deletes cache entry
  // cache.remove("users:123")
}

🔄 The Fixed Flow:

1
User Updates Profile
PUT /users/123 → { "name": "Al" }
2
Database Updated
users table: { id: 123, name: "Al" }
3
Cache Evicted (Deleted)
@CacheEvict removes "users:123" from cache
✅ Old "Alice" data is gone!
4
Next Request
GET /users/123 → Cache Miss → Query DB → Returns "Al"
Fresh data from database! Then cached for next time.
🎯 Alternative: @CachePut

Instead of deleting, you can UPDATE the cache:
@CachePut(value = "users", key = "#id")

Use when: Reads happen immediately after writes
Benefit: Next request is INSTANT (already in cache)
Trade-off: Slightly more complex logic

🏗️ In-Memory vs Distributed Cache

📝 In-Memory Cache
(Your Module)
Server 1
Cache: { "123" → "Alice" }
Server 2
Cache: { } (empty!)
⚠️ Problem:
Each server has its OWN cache!
Inconsistent data across servers
☁️ Redis
(Distributed Cache)
Server 1 →
🗄️ Redis Server
Shared Cache:
{ "123" → "Alice" }
Server 2 →
✅ Benefit:
All servers share ONE cache!
Consistent data everywhere
Feature In-Memory (ConcurrentMap) Redis (Distributed)
Speed ✅ Fastest (JVM Heap) ⚠️ Fast (Network overhead)
Capacity ❌ Limited by JVM (OOM risk) ✅ Terabytes (Separate server)
Consistency ❌ Each server has own cache ✅ All servers share cache
Persistence ❌ Lost on restart ✅ Can persist to disk
Setup ✅ Just annotations ❌ Need Redis server
Cost ✅ Free (built-in) ❌ Infrastructure cost
Best For Small, static data
Single server
Config/settings		 Large, dynamic data
Multiple servers
User sessions
🎯 Production Rule:

• In-Memory → Small apps, configuration data, single server
• Redis → Production apps, user data, microservices, load-balanced servers

📚 Summary

1️⃣
Why Cache?

Database is slow (50ms). RAM is fast (1ms). Cache = Store frequently-used data in RAM for 50x speed!

2️⃣
Cache-Aside Pattern

Check cache first → If found (hit), return it → If not (miss), query DB and store in cache for next time

3️⃣
Spring @Cacheable

Annotation does all the work! Method only runs on cache miss. Magic via AOP (proxy intercepts calls).

4️⃣
Stale Data Problem

Cache can have old data after updates. Solution: @CacheEvict deletes old cache entry when data changes.

5️⃣
In-Memory vs Redis

In-Memory: Fast, simple, single server. Redis: Shared across servers, production-ready, scalable.
