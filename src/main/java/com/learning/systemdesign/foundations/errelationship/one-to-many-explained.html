🎯 The Magic: Foreign Key (user_id)

The child table (POSTS) has a column user_id that stores the parent's ID. This is how we link them!

NOT like this: ❌ Storing an array in the USERS table
YES like this: ✅ Each POST stores which USER it belongs to

🏷️ JPA Annotations Explained

@ManyToOne (Child Side)

Location: In the PostEntity class

Purpose: "Many posts belong to ONE user"

// PostEntity.java
@Entity
public class PostEntity {

  @Id
  private Long id;

  @ManyToOne(fetch = LAZY)
  @JoinColumn(name = "user_id")
  private UserEntity user;
}
What it does:

• @ManyToOne: "I'm the child, I belong to a parent"
• @JoinColumn(name = "user_id"): Creates the column in database!
• FetchType.LAZY: Don't load user data unless I ask
⚠️ This is the OWNING side
This side controls the actual database column
@OneToMany (Parent Side)

Location: In the UserEntity class

Purpose: "ONE user has many posts"

// UserEntity.java
@Entity
public class UserEntity {

  @Id
  private Long id;

  @OneToMany(mappedBy = "user")
  private List<PostEntity> posts;
}
What it does:

• @OneToMany: "I'm the parent, I have many children"
• mappedBy = "user": "Look at the 'user' field in PostEntity for the link"
• This is JAVA ONLY - no database column created!
✅ This is the INVERSE side
Just for convenience in Java code
🎯 Critical Point: mappedBy

Without mappedBy = "user", Hibernate would create a THIRD table called users_posts for mapping!

mappedBy tells Hibernate: "Don't create a new table. The relationship is already managed by the 'user' field in PostEntity."
🌊 What is CASCADE?
@OneToMany(mappedBy = "user", cascade = CascadeType.ALL)
private List<PostEntity> posts;

Cascade = "Domino Effect"

✅ When you SAVE a User

All posts in the list are automatically saved too!

🗑️ When you DELETE a User

All their posts are automatically deleted too! (Cleanup)

🔄 When you UPDATE a User

Changes to posts in the list are saved automatically!

Think of it like: When a parent moves to a new house, the children move too! 🏠➡️🏡
😱 The N+1 Select Problem

This is a MAJOR performance killer in real applications!

🐢 BAD Approach (Naive)

Scenario: You have 10 users. You want to print each user's name and their posts.

// In your controller/service
List<User> users = userRepository.findAll();

for (User user : users) {
  System.out.println(user.getUsername());
  user.getPosts(); // ← DANGER!
}

What Happens:

Query 1:
SELECT * FROM users
Gets all 10 users
Query 2:
SELECT * FROM posts WHERE user_id = 1
For first user
Query 3:
SELECT * FROM posts WHERE user_id = 2
For second user
...
Query 11:
SELECT * FROM posts WHERE user_id = 10
For tenth user
Total Queries: 1 + 10 = 11 queries! 😱
💀 The Horror:

• 10 users = 11 queries
• 100 users = 101 queries
• 1,000 users = 1,001 queries
• Your database will crash! 💥
✅ The Solution: JOIN FETCH

🚀 GOOD Approach

Use a JOIN to load everything in ONE query!

// In your UserRepository
@Query("SELECT u FROM UserEntity u LEFT JOIN FETCH u.posts WHERE u.id = :id")
Optional<UserEntity> findByIdWithPosts(@Param("id") Long id);

What Happens:

Query 1 (ONLY ONE!):
SELECT u.*, p.* FROM users u LEFT JOIN posts p ON u.id = p.user_id
Gets EVERYTHING in one shot!
Total Queries: 1 query! 🎉
🏆 The Win:

• 10 users = 1 query
• 100 users = 1 query
• 1,000 users = 1 query
• Your database stays happy! ✅

💻 How to Implement

1
Validate Parent Exists

Before creating a post, make sure the user exists!

UserEntity user = userRepository.findById(userId)
  .orElseThrow(() -> new ResourceNotFoundException(
    "User not found: " + userId
  ));
2
Link Child to Parent

Set the parent reference in the child entity

PostEntity post = new PostEntity();
post.setTitle(request.getTitle());
post.setBody(request.getBody());
post.setUser(user); // Link to parent!
3
Save the Child

Save the post - the user_id will be automatically set!

PostEntity savedPost = postRepository.save(post);
// Hibernate automatically sets user_id in database!

📚 Summary

1️⃣
One-to-Many = Parent-Child

One user has many posts. One author has many books. One company has many employees.

2️⃣
Foreign Key in Child Table

Child table (posts) has a user_id column that points to parent (users). NOT an array in parent!

3️⃣
Two Annotations

• @ManyToOne in child (PostEntity) - The OWNING side
• @OneToMany(mappedBy) in parent (UserEntity) - The INVERSE side

4️⃣
Beware of N+1 Problem

Use JOIN FETCH to load everything in one query. Otherwise 1,000 users = 1,001 queries!

5️⃣
Always Validate Parent Exists

Before creating a child, check if parent exists. Otherwise you'll get database foreign key errors!
